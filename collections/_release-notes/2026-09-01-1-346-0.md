Today's release includes the following updates:

<span class="tag-ui">ui</span>

- Questionnaires now support a **Date** question type, alongside single select, multi select and free text.
  - When building a questionnaire, choose Date for a question in the Questionnaire Builder, or set the question's `responses_type` to `DATE` in the Google Sheets import.
  - When filling one out in a note, the question renders as a date picker — in the Questionnaire, Review of Systems, Structured Assessment and Physical Exam commands.
  - The captured date carries through charting and carry-forward, and questionnaire responses sent in through the Integration Message Router accept it too.

<span class="tag-bugfix">bugfix</span>

- Fixed an issue in the Canvas Remote app where capturing insurance card images failed when adding a new coverage. The front and back capture steps now load for a coverage that has just been started.
- Discharging an inpatient note now records one discharge and one lock in the note's state history, plus a signature for note types that require one. Previously the lock was written three times, so the state history showed duplicates and plugins subscribed to [`NOTE_STATE_CHANGE_EVENT_CREATED`](/sdk/events/) were notified of the same lock three times.

<span class="tag-api">api</span>

- The FHIR API now carries Date questions. A [Questionnaire](/api/questionnaire/) declares one as `"type": "date"`, and a [QuestionnaireResponse](/api/questionnaireresponse/) answers it with a `valueDate` — an ISO 8601 calendar date — on both read and create.

<span class="tag-sdk">sdk</span>

- A questionnaire can declare a `DATE` question, and a plugin can answer one. Set `responses_type: DATE` when authoring the questionnaire — see [Questionnaires](/sdk/questionnaires/) — and answer it from the [Questionnaire](/sdk/commands/#questionnaire) command by passing a `datetime.date` or an ISO 8601 `YYYY-MM-DD` string as the response.
- Five more records are now readable through the SDK data module, each of them the record behind a command:
  - [Plan](/sdk/data-plan/) — what the [Plan](/sdk/commands/#plan) command records, with its narrative.
  - [FollowUp](/sdk/data-follow-up/) — what the [Follow Up](/sdk/commands/#followup) command records, including the requested appointment date and type, the reason for the visit, and the comments to the patient and to staff.
  - [ReasonForVisit](/sdk/data-reason-for-visit/) — what the [Reason for Visit](/sdk/commands/#reasonforvisit) command records, with its narrative and codings, alongside the configured codings an instance offers.
  - [RemoveAllergyEvent](/sdk/data-remove-allergy-event/) — what the [Remove Allergy](/sdk/commands/#removeallergy) command records, with the allergy removed, the patient, the note and the rationale.
  - [ResolveConditionEvent](/sdk/data-resolve-condition-event/) — what the [Resolve Condition](/sdk/commands/#resolve-condition) command records, with the condition resolved, the patient, the note and the rationale.
- Fixed an issue where calling `find()` with a value set on [FamilyHistory](/sdk/data-family-history/) or [ImmunizationStatement](/sdk/data-immunization/) records raised an error instead of returning results. These value-set lookups now work.

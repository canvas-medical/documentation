Today's release includes the following updates:

<span class="tag-bugfix">bugfix</span>

- Fixed an issue where an automation holding a [Refill](/sdk/commands/#refill) or [Adjust Prescription](/sdk/commands/#adjustprescription) command carried the medication belonging to the patient the automation was saved from. Used on anyone else, the drug stayed off that patient's medication list and was added to the original patient's medication history instead.
  - The medication field now starts empty when one of these commands is inserted from an automation, so the drug is chosen from the patient's own medication list.
  - Saved automations are corrected automatically and do not need to be re-saved.

<span class="tag-ui">ui</span>

- In the Review eligibility window, a payer's note on a copay or coinsurance line now reads inline beside the amount instead of sitting behind an information icon. Lines a payer returns under the same service type, such as a primary care visit and a specialist visit, can be told apart without hovering, so the intended copay is the one saved onto the coverage.
- The Receipts window now names the patient in the Payer column for a payment posted directly to a claim. That column filled in only for payments collected as a patient payment, and was blank for the rest.

<span class="tag-sdk">sdk</span>

- Plugins can now charge a patient's card on file with a new [Charge Stored Card](/sdk/effect-charge-stored-card/) effect. Canvas runs the charge through its configured payment processor, so no card data crosses the plugin boundary.
  - The payment applies to the patient's outstanding balance, or to a single claim when a claim is named. A charge against a named claim can instead be recorded as a copay, which is how a copay or prepayment is collected on a claim that carries no balance.
  - Every charge carries an idempotency key, so retrying one cannot charge the patient twice.
  - The result comes back on a new [`REVENUE__STORED_CARD__CHARGE_RESPONSE`](/sdk/events/#stored-card-charge-events) event rather than from the effect itself, carrying whether the charge succeeded, the processor's payment identifier, and an error code when it did not.
  - A patient's cards on file are readable through a new [PaymentCard](/sdk/data-payment-card/) data model, covering brand, last four digits, expiration, cardholder name, and which card is the default. The stored card token is never exposed.
  - Canvas does not enforce patient consent for a stored-card charge. Obtaining it remains the practice's responsibility.
- Plan- and Procedures-section commands can now be linked through the SDK to an [Assessment](/sdk/data-assessment/) made in the same note: [Plan](/sdk/commands/#plan), [Instruct](/sdk/commands/#instruct), [Follow Up](/sdk/commands/#followup), [Goal](/sdk/commands/#goal), [Update Goal](/sdk/commands/#updategoal), [Close Goal](/sdk/commands/#closegoal), [Stop Medication](/sdk/commands/#stopmedication), [Perform](/sdk/commands/#perform), [Immunize](/sdk/commands/#immunize), and [Task](/sdk/commands/#task).
  - A command in the [commands module](/sdk/commands/) takes the link as an `assessment_id` when it is originated or edited. The matching model in the [data module](/sdk/data/) exposes it as `assessment`, and an [Assessment](/sdk/data-assessment/) lists the commands linked to it.
  - An assessment made in another note is rejected, and the link clears if the assessment is deleted or entered in error.
  - The note builder does not show these links yet. A later release will surface them there, so the commands linked to an assessment appear alongside it in the note.
- The [Medication](/sdk/data-medication/) data model now exposes `latest_sig`, the most recent instructions recorded for a medication, taken from its latest prescription, medication change, or medication statement. Reading it no longer means walking the medication's history.
  - `Medication.objects.with_latest_sig()` loads it for a whole queryset at once.
